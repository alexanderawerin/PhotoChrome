Historical September and maintenance counts elsewhere in the repository do not establish acceptance of this implementation.

The measured comparison is mixed. In the **first series**, eight-key bursts improved 68.6%/74.2% (1200/393 px), peak CDP backing storage fell 46.5%/45.6%, and observed main-thread long-task duration fell 92.0%/90.6%. Individual Manual latency increased 16.8%/9.8%; film-change latency improved 34.5% at 1200 px but increased 19.6% at 393 px.

The portable repeat completed all actions. At 1200 px, film/Manual/burst medians changed **484.55→336.00 / 239.30→285.25 / 1460.90→381.15 ms**, and peak backing storage **736.86→394.47 MB**. At 393 px, the medians changed **298.95→358.95 / 289.70→284.75 / 1492.65→427.15 ms**; backing storage changed **723.04→477.00 MB**, a 34.0% reduction with a higher optimized peak than the first series. Main-thread long-task totals changed **16458→1330 / 14419→1464 ms**. Each eight-key burst produced six preview paints before and one after. Both JPEG and all four ZIP-member bytes matched again.

Across measured runs, peak backing reductions range **34.0–46.5%**. Desktop Manual and narrow film changes remain slower; narrow single-Manual direction is not stable across the two series. Moving work to the existing worker does not prove lower total CPU cost. Two full runs per revision/viewport, each with six intra-action trials, do not establish a confidence interval or a portable device-safe limit. The linked performance report retains raw trials, hashes and measurement scopes.

## Platform and later-work gates

- **AAC-capable browser:** Run supported-source signal/offset/end-time tests using a browser that supports the exact queried encoder configuration. The forced initialization-failure case passed with the real supported decoder and an injected encoder failure. System Chromium lacked this capability; a skipped capability test is not a passed sound-preservation test.
- **Firefox:** Installation was attempted and failed with HTTP 403 **Domain forbidden** from the Playwright browser CDN. The local log is `/tmp/photochrome-work/firefox-install.log`. No new Firefox acceptance is claimed.
- **Safari:** Safari/macOS was unavailable in this Linux environment. MP4 capability reporting, source orientation, geometry/audio synchronization, cancellation and disposal remain unverified there.
- **Physical mobile devices:** No iOS/Android device checks were performed. Desktop Chromium viewport and trusted-touch emulation do not establish decoder/GPU/memory or accessibility behavior on those devices.
- **Project exclusions:** Both configured Chromium projects passed. The desktop project excludes two mobile-only completion cases; those passed in `mobile-chrome`. Mobile excludes six desktop-only cases, covered by the desktop project. These project splits are distinct from the single AAC capability skip. Emulation does not replace the physical-device gate above.
- **Measurement limits:** #14/#15 now have an actual before/after comparison and implementation backed by that workload, documented in the [performance report](film-first-performance.md). These runs do not establish physical-device memory safety, native allocation attribution or a portable new upload budget. Existing upload limits remain unchanged.
